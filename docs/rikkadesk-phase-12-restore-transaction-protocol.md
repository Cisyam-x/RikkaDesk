# RikkaDesk Phase 12 Restore Transaction Protocol

This document defines the Phase 12 P2-C0 protocol and records the P2-C1 offline staging, P2-C2 journaled directory commit, and P2-C3 startup reconciliation implementations. These are internal backend safety primitives only. They expose no restore HTTP API, Tauri command, or UI, do not restore portable secrets, and do not modify the current schema.

## Current Boundary

- App version remains `0.1.0`.
- State schema remains `6`.
- Provider import/export remains version `4`.
- Portable backup format remains `rikkadesk-backup` version `1`.
- Mode A (`state-only`) and Mode B (`full-local-data`) export are implemented.
- Format v1 validation and no-write dry-run are implemented.
- P2-C1 offline Mode A/Mode B candidate staging is implemented with complete package revalidation, fresh Provider references/file storage keys, capacity gating, atomic staged-state write, streamed blob copy, and independent validation before and after publication.
- P2-C2 implements a mandatory rollback snapshot, atomic restore journal, same-parent directory commit, and handled-failure rollback behind an internal offline gate.
- A successful P2-C2 commit stops at `commit-new-moved` and returns `PendingStartupValidation`.
- P2-C3 now reconciles journal plus directory topology before any state load/default/migration/write, revalidates provisional candidates, completes startup ownership before listener readiness, and fails closed or restores the old current when safe.
- Restore UI/API, package selection, shutdown/restart orchestration, progress reporting, and artifact cleanup are not implemented.
- Mode C, ZIP, merge restore, schema migration during restore, and stream resume remain deferred.

The sole format v1 authority is `docs/rikkadesk-phase-12-backup-package-format.md`. A dry-run report is informational and is never authorization to skip validation during an actual restore.

## Decision: Actual Restore Is Offline

Actual restore must not run inside the active mock API process. RikkaDesk must be fully closed, and a future startup maintenance flow, dedicated offline helper, or pre-restart command must own the operation.

Before commit, the executor must establish all of these gates:

- no RikkaDesk process
- no mock API listener
- no active generation or SSE producer
- no backup export
- no file, Provider, state, or SecretStore transaction
- no open application-owned handle under the current `mock-api` directory
- no concurrent restore operation

On Windows, process and handle checks must fail closed. Restore must not ask a tester to disable Defender, SmartScreen, Smart App Control, or enterprise policy.

### Why Live In-Process Restore Is Rejected

A live restore cannot safely reconcile all runtime and filesystem owners:

- component locks and the commit barrier describe the current in-memory state
- active generations, SSE channels, and runtime registries are not persisted
- Windows directory/file handles can block or partially sequence rename operations
- replacing disk state does not replace already loaded in-memory objects
- ManagedBlobStore and SecretStore references are bound to the old app-data layout
- a later live save could overwrite restored disk data with the pre-restore state

No public HTTP endpoint may accept a backup path and replace app data. A native folder picker and restart orchestration belong to a later UI phase, not to the mock API.

## Directory Layout And Same-Volume Rule

For one generated operation ID, the future executor uses sibling directories under the app-data parent:

```text
<app-data>/
|-- mock-api/
|-- mock-api.restore-stage.<operation-id>/
|-- mock-api.pre-restore.<operation-id>/
|-- mock-api.failed-restore.<operation-id>/
`-- restore-journal.json
```

Rules:

- The current directory, staging directory, rollback snapshot, failed-restore directory, and journal must be on the same volume.
- The journal stays outside `mock-api` so a directory rename cannot hide it.
- The operation ID is generated by the program and contains only a controlled ASCII format.
- User input, package names, Provider IDs, file names, and timestamps supplied by the package are never used as directory names.
- Paths are never included in the journal, safe errors, UI summaries, or logs.
- Existing directories for another operation ID are never overwritten or removed automatically.

The failed-restore directory is created only by renaming a rejected new `mock-api` directory during rollback. It is diagnostic local data and is not portable or shareable.

## Two Different Backup Concepts

### Portable Backup Package

The format v1 Mode A/B package is intended for controlled transfer or recovery:

- sanitized state
- optional active managed blobs in Mode B
- no API keys
- no SecretStore or DPAPI blobs
- no source absolute paths
- no usable source-machine secret references

It is validated using the P2-B validator and remains immutable source input.

### Mandatory Local Rollback Snapshot

The pre-restore rollback snapshot exists only to undo this one restore operation:

- it is the complete current `mock-api` directory
- it may contain current state, managed blobs, corrupt/stale diagnostics, and encrypted secret blobs
- encrypted secret blobs are preserved as opaque files without reading, parsing, decrypting, hashing for display, or logging their contents
- it is not a portable package and must never be shared, uploaded, attached, committed, or sent to Codex/ChatGPT
- it retains the current machine/user DPAPI boundary

The preferred snapshot operation is same-volume directory rename, not a recursive copy. The current `mock-api` directory must be durably preserved as `mock-api.pre-restore.<operation-id>` before the new directory can become official.

The rollback snapshot is not deleted immediately after success. Cleanup policy requires a later explicit retention decision and must never run before startup validation completes.

## Source Revalidation And Staging Trust Boundary

Actual restore starts by calling the full P2-B validator again. It must not reuse a prior dry-run report, `ValidatedRestorePackage`, hash map, or planned reference/key.

Required sequence before touching current app data:

1. Open the selected format v1 directory package through a trusted local caller.
2. Re-enumerate the complete package tree.
3. Re-read and validate manifest, format, schema, state, checksums, mode, and blob set.
4. Create a unique same-volume staging directory with create-new semantics.
5. Copy only allowlisted package content into staging while rechecking size and SHA256.
6. Stop reading the source package after the staging copy is complete.
7. Build the new `state.v1.json`, managed blob layout, and empty/no secrets layout inside staging.
8. Re-enumerate and validate the complete staged `mock-api` tree.
9. Re-read the staged state and re-hash staged blobs.
10. Reject any source or staging change, mismatch, unknown entry, link/reparse point, or unsafe path.

Commit operations use only the validated staging copy. If the source package changes during validation or copy, staging fails and current data remains untouched.

## Complete Staging Layout

The staging directory must be independently bootable as a `mock-api` directory:

```text
mock-api.restore-stage.<operation-id>/
|-- state.v1.json
|-- files/
|   `-- blobs/
`-- secrets/
```

The `secrets` directory may be empty or absent according to the eventual startup contract. It must never contain data copied from a portable Mode A/B package.

### Mode A Staging

- Write the fully normalized format v6 state as `state.v1.json`.
- Keep attachment metadata and message parts.
- Generate fresh file storage keys and controlled relative paths in staged state.
- Leave `files/blobs` empty.
- Mark all Providers as having no usable secret.
- Accept that active attachment metadata can resolve to unavailable content after restore.

Mode A does not silently tombstone files or delete attachment parts.

### Mode B Staging

- Generate a fresh storage key for every managed file metadata record.
- Copy each active package blob to `files/blobs/<fresh-storage-key>`.
- Update staged `storageKey` and `relativePath` fields.
- Preserve tombstoned metadata but do not copy a tombstoned blob.
- Require exactly one staged blob for every active metadata record, including unreferenced active files.
- Recheck staged size/SHA256 against the verified package plan.

No original display name or package path becomes a disk file name.

### Provider Normalization

- Generate a new local controlled `secretRef` for every Provider during each actual staging attempt.
- Do not reuse the deterministic P2-B dry-run placeholder.
- Do not trust or reuse a package/source-machine `secretRef`.
- Do not create a secret blob.
- Synchronize settings Provider metadata with the fresh references.
- Expose every restored Provider as `hasSecret: false` until the user manually enters an API key.

Fresh references and storage keys are operation-local staging data. They must not be logged or included in journal/report output.

## Restore Journal Format

The journal is a small safe state machine record:

```json
{
  "format": "rikkadesk-restore-journal",
  "version": 1,
  "operationId": "<generated>",
  "phase": "staging",
  "mode": "state-only",
  "createdAt": "<UTC>",
  "safeErrorCode": null
}
```

Allowed phases:

- `staging`
- `backup-current`
- `commit-old-moved`
- `commit-new-moved`
- `startup-validation`
- `completed`
- `rollback-required`
- `rollback-completed`
- `rollback-failed`

The journal must not contain:

- any path
- conversation/message text or metadata
- Provider configuration
- file names, MIME details, or blob content
- storage keys or secret references
- API keys, credentials, or encrypted secret content

Each transition uses a unique temp journal file, `write_all`, `flush`, `sync_all`, and atomic replacement. Initial creation uses create-new semantics and never overwrites an existing journal. The executor syncs the parent directory where the platform provides a reliable primitive. Windows currently uses a best-effort directory-handle barrier because a portable directory `fsync` equivalent is unavailable; complete power-loss durability is not claimed. A journal transition is written only after the preceding filesystem action is observed.

Journal creation does not make an incomplete staging directory official. Directory existence and journal phase must agree; ambiguity fails closed.

## Commit Protocol

After package and staging validation pass:

1. Recheck disk space and same-volume constraints.
2. Recheck the offline process/listener/handle gate.
3. Confirm no unrelated restore directory conflicts with this operation.
4. Write journal phase `staging`.
5. Write journal phase `backup-current` immediately before preserving current data.
6. Rename current `mock-api` to `mock-api.pre-restore.<operation-id>`.
7. Verify the current path is absent and rollback path is present.
8. Write journal phase `commit-old-moved`.
9. Rename `mock-api.restore-stage.<operation-id>` to `mock-api`.
10. Verify the new current path is present and staging path is absent.
11. Write journal phase `commit-new-moved`.
12. Run complete offline startup validation against the new `mock-api` directory.
13. Write journal phase `startup-validation` only after validation succeeds.
14. Permit mock API startup.
15. After startup ownership is established without integrity failure, write journal phase `completed`.

Forbidden operations:

- deleting current `mock-api` before preservation
- directly overwriting `state.v1.json`
- exposing new state and blobs in separate commits
- copying blobs into the current directory before its rename
- creating the rollback snapshot after publishing new data
- continuing startup while journal/directory state is ambiguous

Directory rename is the commit boundary. The protocol does not claim complete power-loss atomicity; the journal and crash-recovery matrix make every observable boundary recoverable or fail-closed.

## Startup Validation

Before the new mock API can perform any write, offline validation must confirm:

- `state.v1.json` is readable format v6 state
- IDs, Providers, models, custom request config, and file metadata satisfy current invariants
- no Provider has a usable secret blob from the portable package
- every Mode B active file resolves to exactly one staged managed blob
- Mode A has no managed blob requirement and retains unavailable attachment reporting semantics
- no unexpected file, directory, symlink, junction, or reparse entry exists
- no temp restore write remains inside the new current directory

Startup must not create default state after restore validation failure. The failed new directory is preserved for diagnosis and rollback is attempted.

## Rollback Protocol

### New Directory Rename Fails

If staging cannot be renamed to current after old data moved:

1. Write `rollback-required` if possible.
2. Verify the current path is absent.
3. Rename `mock-api.pre-restore.<operation-id>` back to `mock-api`.
4. Revalidate the restored original directory before allowing startup.
5. Preserve staging and journal for controlled later cleanup.
6. Write `rollback-completed` only after the restored original directory passes read-only validation.

### Startup Validation Fails

If the new current directory fails offline startup validation:

1. Write `rollback-required`.
2. Rename failed new `mock-api` to `mock-api.failed-restore.<operation-id>`.
3. Rename the rollback snapshot back to `mock-api`.
4. Revalidate the original directory.
5. Do not create default state.
6. Keep the failed directory and journal for local diagnosis.
7. Write `rollback-completed` only after the restored original directory passes read-only validation.

### Rollback Fails

If any rollback rename or validation fails:

- write `rollback-failed` if possible
- stop without launching RikkaDesk
- retain journal, staging, rollback, current, and failed directories exactly as found
- do not overwrite, merge, delete, or initialize any directory
- require explicit manual recovery

Manual recovery guidance must use safe phase/directory labels and must not print file contents, encrypted blobs, or absolute paths in shared reports.

## Crash-Recovery Matrix

| Observed phase/state | Official data | Startup allowed | Recovery action |
|---|---|---:|---|
| Crash before staging/journal | Existing `mock-api` | Yes after confirming no operation artifacts | Leave current data unchanged; no commit began. |
| Crash during staging | Existing `mock-api` | Yes only after recovery marks operation abandoned | Validate current data; retain/remove incomplete staging only through later controlled cleanup. |
| `staging` or `backup-current`, old directory still current | Existing `mock-api` | No until recovery check completes | Abort operation; current data remains authoritative. |
| Old moved, new not moved (`commit-old-moved`) | `pre-restore` rollback snapshot | No | Conservatively rename rollback to current; do not guess or publish staging automatically. |
| New moved, startup not validated (`commit-new-moved`) | New current is provisional; rollback remains authoritative recovery source | No | Re-run complete offline validation; on any uncertainty, preserve failed new directory and rollback. |
| Startup validation succeeded, journal not advanced | New current after repeated validation | No until phase reconciliation | Re-run validation, then write `startup-validation`; never trust only an in-memory prior result. |
| `startup-validation`, app not yet started | New current | No until ownership completes | Revalidate and load state without side effects, establish state/storage ownership, record `completed`, then permit router/listener readiness. |
| `completed` | New current | Yes | Retain rollback snapshot according to policy; do not delete immediately. |
| Crash during rollback | Rollback snapshot if intact; otherwise ambiguous | No | Re-enumerate all operation directories and continue only an unambiguous rollback. |
| `rollback-failed` or conflicting directories | None selected automatically | No | Stop for manual recovery; never create default state. |

Recovery always revalidates filesystem state. A journal phase alone is not proof that the corresponding rename completed, and directory existence alone is not permission to skip journal reconciliation.

## Disk-Space Gate

Before staging, calculate a conservative requirement containing:

- complete staged `state.v1.json`
- complete Mode B active blob bytes, or only state/metadata for Mode A
- journal and temporary control-file overhead
- filesystem allocation/metadata overhead
- explicit safety margin

Because the rollback snapshot is a same-volume rename, the current `mock-api` size is not counted as a second full copy. The current directory must nevertheless remain on the same volume and be renameable. Cross-volume staging or rollback falls back to failure; this protocol does not define a copy-based commit.

If free space is insufficient or cannot be determined safely, fail before journal/commit and leave current data unchanged.

## Safe Errors And Logging

Future errors use fixed operation/phase codes only, for example:

- restore offline gate failed
- restore staging validation failed
- restore current snapshot rename failed
- restore staged publish failed
- restore startup validation failed
- restore rollback failed

Logs, journal, UI, and reports must not include absolute paths, user names, state/chat content, file names, storage keys, secret references, API keys, request bodies, encrypted secret bytes, or blob bytes.

## Implementation Split

### P2-C1: Offline Staging Builder (Completed)

- Re-run P2-B validation for every attempt.
- Copy the verified package into same-volume controlled staging.
- Generate fresh Provider references and managed-file storage keys.
- Build and fully validate staged Mode A/B `mock-api` layout.
- Add tamper, resource-limit, and no-SecretStore tests.
- Do not rename current app data.

The implementation accepts only a package root and trusted app-data parent. It has no `MockApiState` or SecretStore parameter, creates only its own `mock-api.restore-stage.tmp.<operation-id>` and validated `mock-api.restore-stage.<operation-id>` directories, and never creates a rollback snapshot or restore journal. Forty-six dedicated synthetic tests cover Mode A/B, fresh normalization, TOCTOU/hash checks, capacity, strict layout, failure cleanup, publication, independent revalidation, and unchanged current data.

### P2-C2: Rollback Snapshot, Journal, Commit, And Rollback (Completed Internally)

- The commit API accepts only a trusted app-data parent and a controlled numeric operation ID. It derives current, stage, rollback, failed-new, and journal paths internally and rejects traversal, links/reparse points, collisions, an existing journal, or unrelated restore artifacts.
- A process-wide mutex plus a trusted offline gate prevents concurrent or active-runtime commit. The offline gate is checked before validation and again immediately before the first directory rename.
- The candidate stage is freshly re-opened and validated with the P2-C1 validator. Current data is prevalidated read-only from schema 6 state and structural directory metadata; encrypted secret blobs are preserved opaquely and are never opened, enumerated, decrypted, copied, or logged.
- The commit order is fixed: journal `staging`/`backup-current`, rename current to the mandatory rollback directory, record `commit-old-moved`, rename stage to current, record `commit-new-moved`, and revalidate the provisional new current.
- If publication fails after the old directory moved, rollback restores the original directory and records `rollback-completed`. If the provisional new current exists, it is first preserved as `mock-api.failed-restore.<operation-id>`, then the original directory is restored and validated.
- A rollback rename or validation failure records `rollback-failed` when possible, retains all evidence, blocks automatic continuation, and returns a fixed manual-recovery error. Journal update ambiguity also fails closed.
- Success returns only `PendingStartupValidation`; it does not write `startup-validation` or `completed`, start the mock API, delete the rollback snapshot, or clean operation artifacts.
- Fifty-seven dedicated synthetic tests cover validation, operation IDs, conflicts, journal create/write/flush/sync/replace faults, both rename boundaries, rollback success/failure, journal ambiguity, concurrency, secret opacity, and the P2-C3 success boundary.

### P2-C3: Startup Validation And Interrupted-Restore Recovery (Completed Internally)

- `mock_api::start` runs reconciliation before SecretStore construction, `MockPersistence` loading, default initialization, migration, corrupt/pre-migration backup, runtime registries, router construction, and listener binding.
- A bounded strict journal reader rejects malformed/future/unknown/link journals. Direct-child artifact inventory rejects case collisions, links/reparse points, operation mismatches, multiple dangerous operation IDs, rollback/failed artifacts without a main journal, and ambiguous topology.
- No-journal startup preserves stage-only candidates without publishing them. Normal first-run startup still reaches the existing P1-B NotFound initialization only when no dangerous restore artifacts exist.
- `staging`, `backup-current`, and `commit-old-moved` reconcile conservatively to the old current and `rollback-completed`; they never continue an interrupted publish.
- `commit-new-moved` and `startup-validation` re-run the strict candidate validator. A valid candidate advances/retains `startup-validation` and yields an unforgeable operation token. Invalid or ambiguous provisional data is preserved as failed-new where possible and the rollback snapshot is restored and read-only validated.
- Provisional state loading uses an exact-schema, no-default, no-migration, no-corrupt-backup path. After state and managed-storage ownership exists, the matching token compare-checks journal operation/mode/phase and atomically writes `completed` before router/listener readiness.
- Provisional load failure transitions to rollback, preserves the rejected current, restores and validates the old current, records `rollback-completed`, and returns a safe startup failure without same-process retry/default initialization.
- `rollback-completed` is an independent safe old-current terminal state. `rollback-failed`, malformed journals, operation mismatch, topology conflicts, and failed recovery block startup and retain evidence.
- `completed` uses normal P1-B loading and may retain its rollback snapshot and populated local secrets; later ordinary state/listener failures do not automatically roll back a completed restore.
- Journal and rollback/failed/stage artifacts are retained. No cleanup, portable-secret restoration, API/UI, Mode C, ZIP, merge, schema restore migration, orphan GC, or stream resume is implemented.
- Seventy-four dedicated synthetic P2-C3 tests cover journal parsing, topology/phase crash states, token ownership, guarded loading, completion ordering, rollback faults, concurrency, normal first-run behavior, and secret opacity.

### P5: User Orchestration

- Native folder picker and package preview.
- Explicit full-replacement confirmation.
- App shutdown/restart orchestration.
- Safe progress/status messages without paths or content.

- crash after new moved

Every test uses synthetic temp directories, state, package bytes, and opaque non-secret blob fixtures. No test reads real app data, a real user backup, `mock-api/secrets/*.bin`, or a real API key.

## P2-C0 Conclusion

- Actual restore is offline only.
- Dry-run is not restore authorization.
- The portable package never contains secrets.
- The mandatory local rollback snapshot can retain encrypted secret blobs opaquely for same-machine rollback only.
- Actual restore generates fresh Provider secret references and file storage keys.
- Current data is preserved by rename before staged data becomes official.
- Journal and startup validation prevent ambiguous state from launching.
- P2-C does not support merge restore, Mode C, ZIP, schema auto-migration, or stream resume.

P2-C1 through P2-C3 now complete the internal backend safety chain from validated staging through journaled commit and startup reconciliation. The recommended next step is a Phase 12 total acceptance pass before any P5 user orchestration; restore must remain unexposed until that acceptance confirms the full synthetic chain and documented residual risks.
